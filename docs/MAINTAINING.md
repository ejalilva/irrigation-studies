## Research landscape table

The page fetches `data/papers.json` at load time, so it must be served over HTTP. Opening the file directly (`file://`) leaves the table empty. To preview locally:

```bash
python -m http.server   # then open http://localhost:8000
```

Each paper is one object in `papers`:

```json
{
  "id": "10.1016/j.rse.2019.111226",
  "title": "Quantification of irrigation water using remote sensing of soil moisture in a semi-arid region",
  "authors": "Jalilvand, E., Tajrishy, M., Ghazi Zadeh Hashemi, S.A., Brocca, L.",
  "first_author": "Jalilvand",
  "year": 2019,
  "date": null,
  "venue": "Remote Sensing of Environment",
  "doi": "10.1016/j.rse.2019.111226",
  "url": null,
  "status": "published",
  "type": "article",
  "questions": { "where": false, "when": false, "how_much": true },
  "domain": "Agricultural plains south of Lake Urmia, Iran",
  "region": "Asia",
  "scale": "regional",
  "period": { "start": 2012, "end": 2015 },
  "approach": "SM2RAIN inversion of coarse satellite soil moisture",
  "methods": ["sm"],
  "data": ["AMSR2"],
  "keywords": ["SM2RAIN", "irrigation water use", "AMSR2", "semi-arid"],
  "summary": "One plain-language sentence.",
  "note": null,
  "resources": [
    { "type": "data", "label": "Zenodo", "url": "https://doi.org/10.5281/zenodo.0000000" },
    { "type": "code", "label": "GitHub", "url": "https://github.com/owner/repo" }
  ],
  "resources_checked": "2026-10-21",
  "added": null,
  "needs_review": false,
  "source": "seed"
}
```

| Field | Notes |
|---|---|
| `id` | Lowercase DOI, or the URL when there is no DOI. Used for de-duplication. |
| `status` | `published` or `preprint`. Preprints get a pulsing "not yet peer reviewed" badge. |
| `date` | `YYYY-MM-DD` publication or posting date. Rows within 90 days get a **New** badge. `null` if unknown. |
| `questions` | Whether the study maps where irrigation occurs, detects when it occurs, or estimates how much water is used. |
| `region` | `Global`, `Africa`, `Asia`, `Europe`, `North America`, `South America`, `Oceania` or `Multiple`. Drives the region filter. |
| `scale` | `field`, `regional`, `national`, `continental` or `global`. |
| `period` | First and last year of data analysed, or `null`. |
| `methods` | Any of `sm` (satellite soil moisture), `et` (ET or thermal), `imagery` (optical or radar), `model` (land surface or Earth system model), `da` (data assimilation), `ml` (machine learning). Drives the approach filter. |
| `note` | Optional extra line in the row's details, such as a preprint's earlier title. |
| `resources` | Optional list of datasets (`"type": "data"`) and software (`"type": "code"`) published with the paper, at most four. Shown as **Data** and **Code** links in the "Data & code" column, and listed in full in the row's details. Add, fix or remove entries by hand at any time. |
| `resources_checked` | Date the agent last looked for data and code links for this paper. Delete it to have the agent look again on its next run. |
| `added` | Date the agent added the row. The table opens newest first; visitors re-sort by clicking a column heading (Year, Study, Study area, Period). |
| `needs_review` | Set by the agent when it could not fill every column. Shown as "Check details" in the review preview only. |
| `source` | `seed` (added by hand) or `agent`. |

## Paper-finding agent

Each run, the agent:

1. Searches [OpenAlex](https://openalex.org) for works that match the phrases in `agent/config.json`, published in the last `lookback_days`, or since 14 days before the table's last update if that is earlier, so no stretch of time is ever skipped. In a backfill run it also searches one past year (see [Backfill](#backfill)). Every result is read, using cursor paging; `max_results_per_query` is only a safety limit, and the report says if it was reached.
2. Skips known and previously seen IDs, Zenodo and figshare copies, and papers that don't mention "irrigation" and any term in `must_mention_any`. Without an API key it also requires "irrigation" in the title; with a key, Claude judges relevance from the abstract. Papers dropped by this cheap check are not stored in `seen.json`, so they are re-checked for free on later runs.
3. Classifies each remaining paper. With `ANTHROPIC_API_KEY` set, Claude Haiku 5.5 reads the abstract and fills every column; papers Claude can't classify (for example after repeated rate-limit errors) are left for the next run, and the error is shown in the pull request description, or the run fails if nothing could be proposed. Without a key, keyword rules fill the questions, methods, data and period, and the row is marked `needs_review`.
4. Checks every preprint in the table for a peer-reviewed version with a near-identical title and the same first author. If it finds one, the row switches to the published DOI and venue, and a `note` records the change.
5. Looks for datasets and software linked to each new paper, and to existing papers not checked in the last `data_links_recheck_days`. Sources: [DataCite](https://datacite.org) records (Zenodo, PANGAEA, figshare, Mendeley Data and others) that cite the paper's DOI, the publisher's "is supplemented by" links in Crossref, and repository links (GitHub, Zenodo, HydroShare, Earth Engine and similar) written in the abstract. Links found for existing papers are listed in the pull request description so they can be checked before merging.
6. Writes `data/papers.json` and `agent/seen.json` only if something changed, and prints a Markdown report. A run that only re-checked papers for links and found none opens no pull request.

The workflow runs every Monday at 13:17 UTC, and can also be started from the Actions tab, with an optional `days` input and a **backfill** tickbox. When there are changes, it opens a pull request from `agent/new-papers`, with the report as its description. The Monday run is skipped while a review is still open, so edits on the review branch are never overwritten; a manual run always runs and replaces any open review. The report ends with how many abstracts Claude read and the approximate API cost.

### Backfill

The backfill fills the table with older papers, one publication year per pull request, newest year first. `agent/backfill.json` holds the next year to search (`next_year`) and the last one (`first_year`, 2015).

- **Start it** from the Actions tab: Find new irrigation papers > Run workflow > tick **backfill**.
- **Each run** searches the recent window as usual, plus all of `next_year`. A year with no new papers is skipped straight to the year before, up to `backfill_years_per_run` years per run.
- **Citation bar.** Papers from the current and previous year (`free_years`) are included whatever their citations. Older papers need at least `per_year` citations per year of age, up to `max`: with the defaults, 6 citations for a paper from 2024, 18 for 2020 and 33 for 2015. Change `citations_for_older_papers` in `agent/config.json` to raise or lower the bar.
- **Chaining.** Backfill pull requests carry the `backfill` label. Merging one starts the next year automatically, so you only review and merge. If a year has more than `backfill_max_per_year` relevant papers, it continues over several pull requests before moving on.
- **Restarting.** Edit `next_year` in `agent/backfill.json` to search a year again. Papers already judged are remembered in `seen.json`, so a repeat run costs little. When `next_year` is below `first_year`, the backfill is finished and stops.
- **Failures.** If a search fails and the run has nothing to propose, the run is marked failed, because no pull request means nothing would start the next year. Run the workflow again with backfill ticked.

### Reviewing a pull request

1. **Preview it.** The pull request description starts with a link to `https://ejalilva.github.io/irrigation-studies/irrigation.html?preview#landscape`. The preview shows the proposed papers on the real page, badged **Proposed**, with **Check details** on rows that have empty columns. Adding `?preview` to the page address works at any time; with no open review it shows the published table.
2. **Untick papers to reject them.** Each paper is a tickbox in the description. Unticking one makes `apply-review.yml` move it to `agent/rejected.json` within a minute; it stays in `seen.json` and is never proposed again. Ticking it again restores it. The preview can lag a few minutes behind because GitHub caches raw files.
3. **Mark Rising papers.** Under each paper is a **Rising** tickbox. Tick it to feature the paper as your pick. To add your note, edit the pull request description and type it after `Note:` on that line; it appears on the pick's card. Unticking removes the pick.
4. **Fix details if needed.** Edit `data/papers.json` on the `agent/new-papers` branch (the preview has an "Edit details on GitHub" link), and set `needs_review` to `false` on rows you complete.
5. **Merge.** The site updates about a minute later.

Run it locally:

```bash
python agent/find_papers.py --dry-run             # report only, no files written
python agent/find_papers.py --days 365            # wider window, writes files
python agent/find_papers.py --backfill            # also search the next backfill year
python agent/find_papers.py --year 2015 --dry-run # search one year without touching backfill.json
```

Environment variables: `ANTHROPIC_API_KEY` and `OPENALEX_API_KEY` (both optional), `LOOKBACK_DAYS` (overrides the config), `BACKFILL` (`true` to backfill), and `REPORT_PATH` (writes the report to a file).

### Configuration (`agent/config.json`)

| Key | Default | Purpose |
|---|---|---|
| `queries` | 9 phrases | OpenAlex search phrases, one request each. |
| `lookback_days` | 60 | Minimum search window for recent papers. |
| `max_results_per_query` | 20000 | Safety limit on results read per phrase and window. |
| `max_new_per_run` | 20 | Cap on recent papers proposed in one pull request. Extra relevant papers stay unseen and are proposed by the next run. |
| `backfill_max_per_year` | 120 | Cap on backfilled papers in one pull request. |
| `backfill_years_per_run` | 4 | How many empty years one backfill run may move through. |
| `citations_for_older_papers` | 1 free year, 3 per year, max 50 | Citation bar for backfilled papers (see [Backfill](#backfill)). |
| `max_classifications_per_run` | 2000 | Cap on Claude calls in one run, which bounds its cost and run time. |
| `must_mention_any` | satellite and model terms | A paper must mention at least one term. |
| `claude_model` | `claude-haiku-5-5` | Model used when an API key is set. |
| `claude_seconds_between_calls` | 1.5 | Pause between Claude requests, to stay under the API's per-minute rate limit. Lower it if your API tier allows more requests. |
| `find_data_links` | `true` | Look for data and code links (step 5). |
| `data_links_per_run` | 80 | Cap on existing papers checked for links in one run. |
| `data_links_recheck_days` | 180 | How long before an existing paper is checked for links again. |

## Essential and Rising

**Essential** comes from the reading list: every paper in `data/reading_list.json` that is also in the table gets a green Essential tag, an "Essential" status filter and a link to its place in the list. To tag a paper Essential, add it to the reading list.

**Rising** papers are your picks among recent work: not essential yet, but worth reading now.

Rising papers live in `data/editor_picks.json`, separate from the table data:

```json
{
  "picks": [
    { "id": "10.1016/j.agwat.2026.110866", "note": "Why this paper matters, in one or two sentences.", "picked": "2026-10-21" }
  ]
}
```

`id` must match a paper's `id` in `data/papers.json`. The page currently does not show Rising papers (the cards above the table, the star tag and the Rising filter were removed to keep the table minimal); the file is kept so picks can be shown again later.

## Essential reading list

`data/reading_list.json` holds the reading list, shown as a grid of small cards with tabs for each group. It is a list of `stages`, each with a `key` (`big`, `where`, `when` or `how_much`, which sets the group's color to match the question colors) and a `title`, plus its `items`. Items are numbered in order across stages. Each item needs `title`, `authors`, `year`, `venue`, a short journal name for the card (`venue_short`, for example `RSE` or `HESS`), a `doi` (or `url`) and a one-sentence `why`, which appears when the card is opened. Reorder, add or remove items freely; the page renumbers itself, and every item that is also in the table is tagged Essential there.

## Repository settings

- **Pages:** Settings → Pages → Deploy from a branch → `main`, `/ (root)`.
- **Workflow permissions:** Settings → Actions → General → Read and write permissions, and tick "Allow GitHub Actions to create and approve pull requests". Without this, the pull request step fails.
- **Secrets (optional):**
  - `ANTHROPIC_API_KEY`: a weekly run of 10 to 20 abstracts costs well under a cent at current [Haiku 5.5 pricing](https://platform.claude.com/docs/en/about-claude/pricing).
  - `OPENALEX_API_KEY`: free, from openalex.org → Settings → API. A weekly run (about 15 to 20 requests) fits in the no-key allowance.
- GitHub disables scheduled workflows in public repositories after 60 days without activity. Re-enable from the Actions tab if that happens.

## Storyline: "Every answer revealed another question"

The irrigation studies are told as six chapters in a small diagram, in place of a list of study cards. The chapter titles follow the seminar "Simulating the largest human intervention in the water cycle":

| Chapter | Year | Lane | Title | Study |
|---|---|---|---|---|
| 1 | 2019 | How much | The Columbus voyage | RSE 2019 |
| 2 | 2021 | Where | The devil is in the details | JSTARS 2021 (Sustainability 2021 noted in its card) |
| 3 | 2023 | How much | Paradigm shift | WRR 2023 |
| 4 | 2026 | When | Patterns in the plot | RSE 2026 |
| 5 | Now | Where | Redraw the map | foundation-model mapping, in progress |
| 6 | Next | How much | Coming full circle | where, when and how much together in NASA LIS with NISAR |

**Layout.**
- **Lanes:** there is one lane per question, in the logical order (Where?, When?, How much?). The lane labels are set larger than the card text so the three questions read first.
- **Chapter cards:** each chapter sits in the lane of the question it answers. It shows the chapter name in words and the year on one line ("Chapter one · 2019"; `chapterName()` in `index.html`), with the question tag after them on narrow screens, the chapter icon, the chapter title, one plain line on what was done, and what it left open. The 80 px icon sits over the card's top-right corner, breaking out of its border.
- **Arrows:** each arrow leaves the middle of a chapter's top or bottom edge (marked by a dot), turns once with a rounded corner in the empty part of the next chapter's lane, and enters that chapter from the left with a solid head. A dotted "combined" bracket joins chapters 3 and 4 into chapter 6 from below, and chapter 5's arrow also enters it.

**Study card.** Hovering or focusing a chapter shows its study card beside it. Clicking or tapping keeps the card open, and Escape or a click elsewhere closes it. A published chapter's card holds:
- the chapter title and seminar subtitle
- the study figure (click to enlarge)
- the journal card
- one finding
- what the chapter left open

Chapters 5 and 6 instead show a short text, the models or parts involved, and a link to the map pop-up ("Where is irrigation?" or "How much water?").

**Phones.** Below 1100 px the chapters stack in order with a small arrow between them. A tapped chapter's card opens under it.

**Editing.** Everything comes from `CHAPTERS` in `index.html`:
- `year`, `q` (`where`, `when` or `how_much`) and `icon`, the name of the chapter's picture in `assets/chapters/`
- `title`, `sub`, `what`, `left`
- for published chapters: `study` (a study `id` in `STUDIES`), `finding` and an optional `also`
- for the last two chapters: `topic`, `more`, `text` and `chips`
- `feeds: true` joins the bracket
- `next: true` gives the dashed border of a future chapter

**Chapter icons.** Ehsan supplied the six icons: `voyage`, `details`, `shift`, `patterns`, `map` and `circle`.
- **Files:** each is saved in `assets/chapters/` as transparent WebP, trimmed to its content and squared at 176 px.
- **Backing:** each icon has a `<name>-back.png` mask, the icon's outline with the gaps between its parts closed, holes filled and a thin margin added. The page fills that shape with the card colour (`--paper`) behind the icon, cut to the card itself (`clip-path` on `.j-ico::before`), so the card's coloured top border and right edge don't show through the icon. Above and beside the card the icon stays fully transparent over the lane. Each mask also covers the border's row from where the drawing starts to the card's top-right corner, so no piece of the border shows beside the drawing. The masks are wired up in `assets/study-grid.css` (`.j-ico-<name>::before`).
- **Cache:** the icons and masks load with a version (`ICON_V` in `index.html`, and `?v=` on each mask URL in `assets/study-grid.css`). Bump both whenever an icon changes; otherwise browsers can keep showing the old picture for up to 10 minutes after GitHub Pages deploys.
- **Changing an icon:** save the new transparent image and rebuild its mask the same way: alpha above 40, morphological closing with a 9 px disk at 256 px, hole fill, a 3 px dilation, then resize to 176 px. An icon whose outline is open, like the dashed `circle` (replaced on 26 October 2026), uses its convex hull instead of the hole fill, so its whole inside is covered. The `shift` icon (paper planes, replaced on 26 October 2026) is scattered, so its backing is a plain disc around the icon's centre, which matches the circle's. Because both are mostly dark line art, they get a thin light halo in dark mode (`.j-ico-circle` and `.j-ico-shift` in `assets/study-grid.css`).

`renderJourney()` draws everything and redraws the arrows when the layout changes. The figures and paper details still come from `STUDIES` and `assets/journals.js`.

**Chapter reader.** Every study card ends with "Read the full chapter →", which opens the whole chapter in a dialog (`#chapter-reader`, built by `chapterHTML()` in `irrigation.html`). Each chapter has its own address, `irrigation.html#chapter-1` to `#chapter-6`, so a chapter can be linked directly. The reader shows, in order:
- the chapter's story: `story`, a list of paragraphs written from Ehsan's account of how each study led to the next and from the old site's "Irrigation studies" section
- the study's figures, chosen by index into the study's `images`: `lead` (one full-width figure), `compare` (two figures on a slider; Chapter four's 2021 and 2022 irrigation-day maps, as on the old site's Juxtapose embed) and `readFigs` (the rest, side by side). Each figure enlarges on click.
- "What the study found": the study's `findings`, from the old site's bullets
- the journal card with the chapter's `finding`, the `also` study, `chips`, and what the chapter left open
- `links` (for example AgroTrack on GitHub) and `posts`: social-media posts about the study, each with `who`, `handle`, `date`, `url` and a one-line `text` in our own words
- previous and next chapter buttons; the arrow keys also move between chapters

Closing the reader returns focus to the chapter last read and sets the address back to `#studies`. The reader's styles are at the end of `assets/study-grid.css` (`.chapter-reader`, `.cr-*`, `.cmp` for the slider).

## Figures

The study figures appear in the storyline's study cards (see above) and enlarge in a dialog when clicked. `assets/study-grid.css` styles the storyline, the study cards and that dialog. Each study's figure is its `image` (`src`, `alt`, `caption`, `source`, optional `credit`), or the first of its `images`. A chapter with `figs: 2` shows the first two of its study's `images` side by side, and each enlarges on its own. "Patterns in the plot" uses this to show the 2021 Central Valley irrigation-day map next to Fig. 8a of the paper, the Nebraska irrigation-schedule heat map with the season start and end that AgroTrack detected. That heat map was extracted from the article PDF and saved as `assets/studies/agrotrack-heatmap.webp`; its source is recorded in `data/study-figure-sources.json`.

Three figures were retrieved from Ehsan's personal irrigation page on October 22, 2026 and saved locally under `assets/studies/`. `data/study-figure-sources.json` records their DOI associations and source URLs. WebP conversion is lossless, with original pixels and transparency retained.

The Rabiei et al. (2021) figure was not found on the personal page. Its existing journal Figure 13 was retrieved successfully through the browser, saved locally, and credited to the paper (CC BY).

AgroTrack uses the original 2021 and 2022 irrigation-day maps from the Juxtapose comparison embedded on the personal irrigation page. Both are saved locally as original PNGs and displayed side by side, with individual enlargement controls. All five studies have figures. Use an `image` object (`src`, `alt`, `caption`, `source`, optional `credit`) for one figure, or an `images` array for a comparison. Failed image loads are explicitly labeled instead of replaced by synthetic resolution illustrations.

The journey page (`journey.html`) is linked as "My journey" in every page's header, and from the Experience card on About. Its design, data and cut-out landmarks are described in `docs/JOURNEY.md`; `journey-initial.html` keeps the first design for comparison.

## Why irrigation matters and the gap (irrigation.html)

## How the maps show a part's research

`data-popup` on `#explore` (set in both `index.html` and `human.html`) chooses one of three behaviours. To compare them without editing, add `?popup=summary`, `?popup=hover` or `?popup=click` to the page address.

- **`summary` (the default since 26 October 2026).** Hovering a part plays its animation at once. After `SUMMARY_DELAY` (900 ms, in `assets/water-cycle.js`), the text under the part's label appears: no box, the same transparent background and page-colour halo as the plain description. It holds:
  - the one-line description;
  - a chip for each paper (journal short name and year, in the journal's colour from `assets/journals.js`);
  - counts of other work (`3 papers · 4 ongoing · 3 planned`), worked out from each project's status: "planned" or "not started" counts as planned, "earlier" or "contribution" as earlier, and anything else as ongoing;
  - "Click to explore".

  A click on the part or on the text opens the dialog.

  **Placement.** The text goes under the label first, then above it, then beside it. It takes the first spot that stays inside the map (it may hang up to 64 px into the page margin under the map) and covers no other map label.
  - Parts with a pinned spot (`data-desc="x y start|end"`, such as Runoff & rivers and Human-driven processes) keep it.
  - Lakes has `data-desc="above"`, because text under its label would cover the lake.

  During the tour the description stays plain. On phones and touch screens it appears at once on tap, and a second tap opens the dialog.
- **`hover`.** A panel with the part's full research (the same content as the dialog, built by `fillTopic()`) opens over the side of the map that covers the part least. It is 300–400 px wide, fills the visible height of the map and scrolls inside. Moving into it keeps it open, a click pins it, and Escape, × or a click elsewhere closes it; ⤢ opens the dialog. Ehsan found this too busy; it is kept for comparison.
- **`click`.** The original behaviour: a plain one-line description under the label at once, and a click opens the dialog.

### Hosting PDFs

PDFs live in `assets/papers/`. Only post a published PDF when the paper's license or publisher allows it:

- **Open access** (CC BY, CC BY-NC-ND): yes, unmodified and credited. This covers JSTARS 2021, Sustainability 2021, Climate 2022, JAG 2022 and Frontiers 2026.
- **AGU (WRR):** the final PDF can be posted 6 months after publication if the AGU copyright statement is visible on it ([AGU author policies](https://www.agu.org/publications/authors/policies)). WRR 2023 is posted. The 2026 commentary can be posted from March 2027.
- **Elsevier subscription articles** (RSE 2019, J. Hydrol. 2018, COMPAG 2024, ISPRS J. 2024, RSE 2025, RSE 2026): the published PDF cannot be posted publicly. The accepted manuscript can, on a personal site, with a CC BY-NC-ND license and a link to the DOI ([Elsevier sharing policy](https://www.elsevier.com/about/our-business/policies/sharing)). To share these, add the accepted manuscripts as `pdf`, with a first-page note naming the license and the DOI.

## Water-cycle explorer

The two landscapes are inline SVG in `index.html` and `human.html`, so they work under the GitHub Pages repository path without an iframe or external hosting. Update project text and status labels in the `topics` object in `assets/water-cycle.js`. The controller is isolated from the existing studies and literature scripts. Animations run on hover or keyboard focus and respect reduced-motion settings. On touchscreens, one tap highlights a map area and a second tap opens it. The map is kept deliberately sparse: there is no instruction text, list of parts or touchscreen note around it. When a part is highlighted, its `short` line from `topics` and "Click to explore →" ("Tap again to explore" after a first tap on touchscreens) appear as plain text in the white space just outside the drawing, close to the part; clicking or tapping the text opens the part. The text is always left-aligned. By default it sits right under the part's map label and starts at the label's left edge. For labels left of their badge, `data-desc-right` (map units) marks where the drawing begins to the right, and the text wraps to more lines to stay clear of it. A scene item's `data-desc` attribute changes this: `above` puts it above the label, and `"x y start"` or `"x y end"` pins its top-left or top-right corner to a point in map units (used for Runoff & rivers and the farm, whose nearest white space is under the block). The Soil moisture and Lakes badges sit a little away from the block, and Vegetation & ET and Drainage a little to the left, so their text has white space under the label. The text stays up while the mouse moves onto it, and it is clamped inside the map's box. On phones it sits under the map with the part's title. With nothing highlighted, nothing is shown. The map parts stay keyboard-focusable, so the map is still usable without a mouse.

**Size.** On the main page the map's `viewBox` is cropped to the drawing (`0 65 1130 640`), and on screens wider than about 1110px the map extends into the page margins to within 20px of the window edge, up to 170px each side (`--bleed` in `assets/water-cycle.css`). Phones use their own framing (`frameLandscape` in `assets/water-cycle.js`).

**Updating CSS or JavaScript.** Both pages load `assets/*.css` and `assets/water-cycle.js` with a version query (currently `?v=2026-10-25f`). Change that value in `index.html` and `human.html` whenever you change those files. Browsers keep cached copies for a while, and without a new version a visitor can get the new page with the old styles and script: labels then show large and black, and animations and the tour do not run.

**Soil block.** Both faces of the block are split, in face-local units, into a surface layer (0–14, top 5 cm), a root zone (14–44, to about 1 m) with plant roots, an unsaturated layer (44–56), and groundwater (56–94) whose top is the water table. Each band is drawn in its face's own plane with a `matrix(...)` transform (left face `matrix(1 .51143 0 1 280 390)`, right face `matrix(1 -.39048 0 1 630 569)`), so bands, labels and arrows follow the isometric slope. On hover of Soil moisture the surface wets and dries quickly, a wetting front then fills the root zone and lingers, and water moves up the roots as it dries; keep the `surface-wet`, `wetting-front` and `uptake-show` timings equal so the stages stay in order. Drainage arrows run down the left face from the root zone to the water table. The river ends at a small sea on the front corner of the block (part of Runoff & rivers), shown in section on the block's edge as a shallow wedge rather than a fall down the soil face. The beach stops on either side of the river mouth and the sea starts in the river's colour, so the river runs straight into the sea.

**Corn.** The three plants above the roots are corn: a stalk with arching leaves, a tassel and an ear in its husk with silk. The plant grows from its base (`corn-grow`), and the tassel and ear appear as it matures (`corn-tassel`, `corn-cob`).

**Linked parts.** Some animations belong to two parts: elements with a `data-link` attribute (for example `data-link="soil vegetation"`) run when either named part is highlighted, because the controller gives them the `link-run` class, and the tour restarts and speeds them with that part. Soil moisture and Vegetation share the 7-second soil cycle: the corn above the roots grows as the roots take up water, then forms tassels and yellow cobs. Rain and Runoff & rivers share a 6-second cycle: a shower falls, then the river swells (`river-swell`, a stroke on the river outline) and a plume spreads into the sea before both recede. Keep linked animations at the same duration so they stay in step. In the tour, a linked element plays only on the step of the part named first in its `data-link` (the cause), so the rain falls once, on the Rain step, and the corn grows with the roots on the Soil moisture step.

**Farm (Human-driven processes).** The pivot rotates in the field plane about its central well, making two turns while the pump runs and resting while it is off. Its towers and falling spray ride the arm inside `.pivot-counter` groups, which counter-rotate and undo the field projection so they stay upright; keep the `pivot-turn` and `pivot-counter` timings identical or they drift apart. The well runs from the pivot down to a screen in the groundwater on the right face. The pivot and pump share a 16-second cycle: the pump runs for 12 seconds while the arm makes two 6-second turns (chevrons rise up the well, water in the aquifer moves toward the screen, the pivot sprays), then rests. On the first turn the pivot field goes from dry light brown to wet dark brown behind the arm, and on the second turn from dark brown to green; each layer is a circle whose stroke is as wide as its diameter, revealed with `stroke-dashoffset` so it draws a growing pie. The field returns to bare soil at the end of the cycle. While it runs, a cone of depression forms in the water table around the well. Its shape follows the steady-state Thiem profile, deepest at the well (24 units) and returning to the undisturbed water table 125 units away, and it deepens and widens quickly at first and then more slowly, roughly with the logarithm of time, before recovering the same way once the pump stops. The undisturbed water table shows as a dashed line while the cone is present. Keep `pivot-turn`, `pivot-counter`, `cone`, `pump-on`, `wt-original`, `pump-spray`, `footprint`, `field-wet` and `field-green` at 16 seconds with matching percentages. The farm's tour step is fixed at 5 seconds (`data-tour-step` on its group, up to 4x speed) so the tour shows both turns. The river-fed fields draw from a diversion dam (weir, intake gate and main canal) on the river bend. Each field has its own lateral canal and gets a 4-second turn in rotation (animation delays 0, -8 s and -4 s): its lateral fills and flows, water advances along the furrows, and the bare field turns dark brown or the cropped fields turn greener and their plants grow, then each field slowly dries until its next turn. A CSS animated `transform` replaces an element's SVG `transform` attribute, so animated elements that need a position sit inside a positioned group.

**Labels.** Map labels have a halo in the page colour (`paint-order: stroke`). Badge labels sit on the white margin around the landscape, except Runoff & rivers, which sits on the land beside the river and keeps dark text on a light halo in both themes (`.maplabel.on-map`).

**Snow.** Snowfall, the snow caps, the cloud and sun, the meltwater and a river swell share one 12-second cycle:
- **Snowfall (0–38%):** snow falls from the cloud and the caps build up.
- **Sun (36–46%):** the snow stops and the sun replaces the cloud.
- **Melt (44–82%):** the caps start melting at once, and meltwater runs down the mountain into the river.
- **River (48–92%):** the river swells and spreads its plume into the sea, as it does after rain, and stays high while the caps melt.
- **Reset:** the sun gives way to the cloud for the next snowfall.

The flakes sit in a `.snow-shower` group, the cloud is `.snow-cloud` and the sun `.snow-sun` (opacity 0 by default, so it stays hidden with reduced motion). The meltwater path has the `snowmelt` class. The river swell and plume for snow are copies of the rain ones (`.river-swell-melt`, `.river-plume-melt`, `data-link="snow"`) inside the Runoff & rivers part; a CSS rule keeps them still when that part itself is explored. Keep all of these at the same length and the same -3.6 s delay; the delay makes the still map, and the start of a hover, land late in the snowfall with the caps nearly full. The snow tour step is fixed at 4 seconds (`data-tour-step="4000"`) so the tour shows the whole cycle at 3x speed.

**Intro tour.** When the page opens and the map is at least half in view, after half a second each map part plays briefly in turn, in badge order: 01 Snow & frozen ground, 02 Human-driven processes, 03 Rain together with 04 Runoff & rivers (the river rises in the same step; `data-tour-with="rain"` on the river's group), 05 Lakes, 06 Vegetation & ET, 07 Soil moisture, 08 Drainage. The badge numbers on the map, and the `n` values in `topics`, follow this order; and then the map waits (about 17 seconds on the main page, 5 on the human-driven page). Each step lasts between 1.6 and 3.2 seconds, long enough for the part's slowest animation to finish most of a cycle at up to 3x speed; speeds return to normal when the step ends. While the tour runs, only the part being shown animates. It stops at once if the visitor clicks or taps anywhere, presses a key, focuses a part, or moves the mouse across the map onto a part; a mouse resting or nudged over the map does not stop it. It also stops if the map is scrolled out of view or the tab is hidden. It does not run with reduced motion or when the page opens on a research dialog. Once it finishes or the visitor stops it, the browser remembers this in `localStorage` (`water-cycle-tour-v2-main` and `water-cycle-tour-v2-human`) and later visits skip it; a tour cut short by scrolling or switching tabs plays again on the next visit. Add `?tour` to the page address to replay it as a first-time visitor. The orange **Play tour** button above the map replays it at any time and reads **Stop tour** while it runs, which is also how a visitor stops the automatic tour without touching the map; with reduced motion it steps through the highlights without movement. There is no separate Motion button. The earlier resolution illustration is retained in the expandable “Seeing irrigation at different scales” section.
